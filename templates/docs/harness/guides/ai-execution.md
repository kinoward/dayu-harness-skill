# AI 执行规约

> 触发时机：开始或继续任何由 AI 主导的实施任务时读取。规定人类和 AI 的职责边界、长任务执行方式、自动修复和汇报要求。

## 1. 产品与技术分工

用户负责产品方向、用户体验和边界取舍；AI 负责在这些边界内完成技术方案、实现、验证和文档同步。

必须请示用户：
- 用户旅程、UI 呈现形式、功能是否存在
- 产品边界和面向用户的取舍
- 会改变使用方式、数据风险或发布策略的决定

AI 可自主决定：
- API 契约、架构模式、缓存和错误处理策略
- 测试组织、验证命令、实现拆分和重试方式
- ADR、排障记录和研究记录的草稿内容

## 2. 长任务自主执行

方案确认后，把实现、测试、文档、提交或 PR 链路串起来执行，不在每个机械步骤前停下询问。

执行要求：
- 独立任务可并行推进，互相依赖的任务按依赖顺序执行
- 长耗时命令保留输出证据，失败时先读原始错误再判断
- 每完成一个阶段简短汇报当前状态
- 只有遇到产品取舍、权限缺失或不可自动修复的问题时才停下询问

## 3. 自动修复与重试

当自动化操作因可修复原因失败时，主动诊断并重试。

Commit 被 hook 拒绝：
1. 读取 hook 输出定位违规内容
2. 修正提交信息格式或 issue trailer 位置
3. 重新执行 commit

PR 或 CI 被拒绝：
1. 读取失败日志定位检查项
2. 修正 PR 标题、body、Test plan 或代码格式
3. 重新推送或更新 PR 触发检查

通用规则：
- 同一错误重试 2 次后仍失败，报告用户并说明已尝试的修复
- 重试前必须有实质性修正，不盲目重复命令
- 网络错误可直接重试，连续 3 次失败后报告用户

## 4. Test plan 执行

PR 创建后，主动按 `## Test plan` 清单逐条验证并汇报。Test plan 是要执行的清单，不是装饰。

| 清单项类型 | 执行方式 |
|-----------|---------|
| CI / lint check | 使用 `gh pr checks <N>` 或等价命令核对 |
| 可跑命令 | 直接执行并保留关键输出 |
| GitHub 页面渲染 | 使用 `gh api` / `gh pr view` 抓取可验证信息 |
| 需 merge 后验证 | 标注「需 merge 后验证」，merge 后补跑 |
| 纯视觉无法自动化 | 标注「需人工验证」，列出检查要点 |

汇报时每条清单项一行，附关键证据，不只说「全部通过」。

## 5. Review 自检

每完成一段实现后，对照 review checklist 自查。若已启用 `github.pr` 且文件存在，清单位于 `docs/harness/sensors/reviews/code-review-checklist.md`。

高频问题：
- 资源释放、输入校验、错误处理、并发安全
- 边界条件、日志敏感信息、测试与行为不匹配

## 6. 输出与错误信息

工具自身已经输出详细错误时，不重复贴大段日志，只补充根因、修复动作和下一步。

当需要解释技术决策时，用产品层面的影响描述，而不是把技术选项丢给用户裁决。
