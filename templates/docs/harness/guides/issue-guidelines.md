# Issue 治理指南

> 触发时机：启用 `github.issue`（或明确有 GitHub Issue 流程）时读取。

## 目标

- 用结构化方式表达 Issue 依赖关系，减少“并发修复先后不一致”。
- 让自动化与 AI 能用统一规则识别可执行顺序。
- 保持 Issue 元数据轻量，不依赖标签体系或机器人评论。

## 依赖关系约定

使用 `Depends on: #N` 表示处理顺序：

- `Depends on: #N` 表示当前 Issue 依赖 N 号 Issue，应在 N 号 Issue 之后处理。
- 仅作为顺序提示，不作为阻塞策略，不替代人工风险评估。
- AI/自动化应按依赖方向给出处理建议优先级，但允许在审批和上下文允许时并行推进。

## 与语言和自动化行为相关的边界

- **不打标签**：该能力不自动添加或强制 `label`。
- **不自动评论**：该能力不自动在 Issue 中发表评论。
- **不做语言检查**：该能力不做正文语言规范审查。
- **仅聚焦规范文本**：脚本只校验 `Depends on: #N` 的单行语法格式。

## 快速验证项

1. 检查 `Depends on: #N` 格式是否在正文中出现。
2. 支持的严格单行形式为 `Depends on: #N[, #M]`，并且全文最多出现一行依赖声明。
3. 如果声明依赖失败，提示格式问题；不做 `#N` 解析/存在性校验。

## 配合 release/PR 的说明

- 该规则与 PR closing trailer 协同，但不替代 PR closing 位置校验。
- PR 是否包含 `Closes/Fixes/Resolves` 的校验仍由 PR 能力维护（`github.pr`）。
