# AI 协作风格规约

> 触发时机：开始/继续任何由 AI 主导的实施任务时读取。规定「用户和 AI 各自做什么」以及「AI 在执行长任务时的默认行为」。

## 1. 产品与技术的分工

用户负责整体产品体验把控；技术决策由 AI 自主完成并落文档。

### 用户决定（必须请示）

- 用户旅程、UI 呈现形式、功能是否存在
- 产品边界（规约里的硬性规则）
- 面向用户的取舍（等待时长、降级行为、错误兜底文案）

### AI 自主决定（无需请示）

- API 契约设计、架构模式、缓存策略
- 错误处理策略（重试次数、超时、fallback 路径）
- 性能参数（batch size、并发数、超时阈值）
- ADR 内容与状态推进

### 汇报格式

汇报「我做了什么决定」时，用产品层面的语言而不是技术语言：
- 「这会让首屏等待压到 3 秒」
- 不要列技术选项让用户选——选项太多 = 用户被迫做技术裁决

## 2. 长任务自主执行 + 自动修复

方案确认后，把链路上的所有任务串起来执行，遇错自动诊断修复，不每步停下问。

### 适用场景

- 多步骤实现任务（代码编写 + 测试 + 文档 + commit）
- PR 创建 + CI 触发 + Test Plan 验证 + 合并
- Issue 修复 + 分支 + commit + PR + 自动 merge

### 操作模式

- **后台执行 + 流式追进度**：长任务（test suite、构建、下载等需 30s+ 的操作）用后台运行启动（`run_in_background`），通过 Monitor 流式接收事件。不轮询（不用 `sleep` 循环等待），不阻塞前台。事件到达后汇报「已完成 X/Y」。

- **并行执行**：互不依赖的验证、代码修改、文档更新可在同一轮内并行发送多个工具调用，减少往返延迟。

- **遇错从 raw 输出诊断**：看 stderr / stdout / exit code 的原始输出直接定位根因。不看到 CI "failed" 就重新跑，也不只看 CI summary 忽略具体错误行。诊断后再决定是修复重试还是报告用户。

- **阶段节点简短汇报**：每完成一段（如「lint 通过，开始跑 test」）给一句话进度。不要求用户确认继续——只在遇到产品决策时停下询问。

## 2.1 Auto-Retry 通用约定

当自动化操作因可修复原因失败时，主动诊断并重试，不假设失败是最终结果。

### Commit 被 Hook 拒绝

1. 读取 hook 错误输出，定位违规内容
2. 修正违规内容（如 CJK → 英文、格式不符 → 修正）
3. 重新执行 `git commit`

### PR 创建被 CI 拒绝

1. 读取 CI 失败日志，定位具体检查项
2. 修正 PR 标题、body 或代码格式
3. 重新推送触发 CI

### 通用重试规则

- 同一错误重试 2 次后仍失败 → 报告用户并说明已尝试的修复
- 重试前必须基于错误输出做出实质性修正，不盲目重试
- 网络错误直接重试，连续 3 次失败报告用户

## 3. Test plan 执行与汇报

PR 创建后，主动按 PR body 的 `## Test plan` 清单逐条验证并汇报。Test plan 是要执行的清单，不是装饰。

### 操作流程

1. PR 创建后等 CI 跑完
2. 逐条执行：

| 清单项类型 | 执行方式 |
|-----------|---------|
| CI / lint check | `gh pr checks <N>` 核对 |
| 可跑命令 | 直接跑，关键输出贴出来 |
| GitHub 页面渲染 | `gh api` / `gh pr view` 抓取 |
| 需 merge 后验证 | 标注「需 merge 后验证」，merge 后补跑 |
| 纯视觉无法自动化 | 标注「需人工验证」，列出要点 |

### 汇报格式

每条清单项一行 `✓` / `✗` / `⏸`，附关键证据（CI 状态、命令输出），不要只说「全部通过」。

### 同步到 PR body

PR 合并前，执行通过的条目在 PR body 把 `- [ ]` 改成 `- [x]`，让 PR 页面直观反映真实验证进度。

## 3.1 结构化输出消费模式

本项目的维护脚本（`audit.sh`、`validate.sh`、`diff-helper.sh`、`check-consistency.sh`）遵循统一的结构化输出协议。AI 调用时应：

1. **调用脚本获取结构化数据**：使用 `--json` 模式，stdout 为纯 JSON
2. **提取自然语言描述**：每个脚本的 JSON 输出包含 `description_nl` 字段，可直接作为用户反馈的基础文本
3. **语义增强呈现**：在 `description_nl` 基础上补充上下文和建议操作，以自然语言呈现给用户
4. **按建议行动**：根据 `status`、`recommendation` 等字段决定下一步操作
5. **不自行解析替代脚本输出**：不绕过脚本直接读取原始文件来做判断——脚本是分析质量的底限保证

## 4. 代码 Review 自检

每完成一段实现后，对照代码 Review 自检清单自查。

详见 [code-review-checklist.md](code-review-checklist.md)。

TL;DR 高频问题：资源释放、输入校验、错误处理、并发安全、边界条件、日志敏感信息。

## 5. 错误提示精简

工具自身已经输出了详细错误时，不要重复，只做简短补充。
- 上游 commitlint 已打印完整 type 列表 → 只补「运行 `commitlint --edit` 查看修复建议」

## 6. 开发顺序与测试覆盖

根据项目架构确定开发顺序（如先核心服务再外围功能）。测试先行：
- 每个功能实现前先写测试
- 工具选择参见 [testing-strategy.md](testing-strategy.md)

## 7. 经验沉淀

AI 在每次协作中产生的经验（决策、排障、研究），应在会话结束前主动建议沉淀到 docs/ 对应位置：

| 经验类型 | 沉淀位置 |
|---------|---------|
| 架构/技术决策 | `docs/decisions/` |
| 问题排障 | `docs/troubleshooting/` |
| 研究发现 | `docs/research/` |
| 约束变更 | `docs/practices/` + AGENTS.md |

项目是 AI 经验的唯一归纳场所，不应依赖全局记忆或外部系统。
